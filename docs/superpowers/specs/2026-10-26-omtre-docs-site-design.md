# omtre 文档站设计

- 日期：2026-10-26
- 状态：设计已确认，待实施
- 适用版本：omtre 1.0.0
- 目标：为第一次接触 omtre 的开发者提供一条可完成、可验证、可回查的上手路径，同时完整覆盖现有产品能力、进阶定制和参考资料。

## 1. 背景

omtre 当前以 README 为主要入口，另有设计、发布、上游和技能市场文档。这些材料能说明项目是什么，但第一次接触者需要自己拼出以下信息：

- 应该安装到哪个项目；
- 应该选择哪个平台参数；
- 初始化成功后应该看到什么；
- 第一个任务应该怎么开始；
- Agent 应该产出哪些文件；
- 哪些能力真的可用，哪些平台只是模板适配；
- 质量门、归档、提交、推送之间的边界。

参考站 `https://docs.trytrellis.app/` 的有效做法是：把首次安装、第一个任务、工作原理、日常使用和真实场景放在最前面，再展开进阶与参考。omtre 文档站采用同样的学习顺序，但不照搬其宣传措辞和上游代码路径。

## 2. 已确认决策

1. 首版交付“完整对标目标站”，不是只写大纲或只重写 README。
2. 中文优先；代码、命令和 API 名称保持英文；结构预留未来英文正文。
3. 使用 VitePress 构建静态文档站，通过 GitHub Pages 发布。
4. 内容以 1.0.0 的真实行为和测试为准，主动披露限制。
5. 首次任务改为真实业务小功能，不使用“改文档”作为演示。
6. 用户文档以 `docs-site/` 为唯一真源；`docs/` 保留维护者、发布和上游资料。
7. 站点采用五组主导航：开始使用、使用指南、进阶、参考、资源。
8. 首版不虚构博客、客户案例、Showcase 或版本历史。

## 3. 读者与成功标准

### 3.1 读者

| 优先级 | 读者 | 核心问题 |
|---|---|---|
| P0 | 已使用 AI 编码工具、第一次接触 omtre 的开发者 | 我怎样在现有项目中完成一次有价值的任务？ |
| P1 | Tech Lead / 平台负责人 | 它能不能进项目组？边界、成本和治理风险是什么？ |
| P2 | 进阶用户 | 怎样定制工作流、代理、Hooks、技能和无人值守运行？ |
| P3 | 贡献者 | 怎样改文档、技能、模板和代码？ |

### 3.2 首次使用者成功标准

读者在机器已具备 Node.js、Python、Git 和可用编码代理的前提下，选择一个低风险业务小功能后，能在 20 分钟内完成：

1. 安装并初始化 omtre；
2. 创建并确认一个任务；
3. 看到计划产物；
4. 完成代码与测试改动；
5. 通过仓库已有验证命令；
6. 人工检查 diff；
7. 提交、归档并生成会话日志。

完成首任务后，读者还应能回答：

- omtre 解决什么问题，不解决什么问题；
- `.omtre/spec/`、`tasks/`、`workspace/` 分别保存什么；
- 为什么规范符合性和命令验证不是同一件事；
- 哪些操作仍需要人工确认。

## 5. 首次使用者路径

### 5.1 设计原则

“先完成，再解释”：

```text
认识 omtre
  -> 安装
  -> 第一个业务任务
  -> 验证与归档
  -> 工作原理
  -> 日常使用
  -> 场景与进阶
```

安装页不先讲架构；工作原理页放在首任务之后；参考页只承担查询，不承担教学。

### 5.2 第一个任务的安全边界

首任务必须在读者自己的真实业务仓库中完成，但只能选择：

- 影响不超过 3 个现有源文件；
- 不新增数据库迁移；
- 不修改鉴权、支付、账单、隐私或生产配置；
- 不依赖新的外部服务或凭证；
- 不部署、不合并、不自动推送；
- 能用仓库现有测试框架验证；
- 可以只回滚一个任务分支。

若找不到满足条件的候选任务，文档要求读者停止并改用团队指定的练习仓库，不把高风险改动包装成“第一个任务”。

### 5.3 首任务步骤

1. 检查 Node.js、Python、Git 和编码代理。
2. 在干净分支初始化：

   ```bash
   npm install -g omtre
   omtre init -u <your-name> --qoder
   omtre platforms
   ```

   平台参数按读者实际工具替换；命令示例不能宣称所有平台等价。

3. 确认 `.omtre/`、对应平台目录和个人 workspace 已生成。
4. 让 Agent 先不做改动，提出 3 个符合条件的候选业务功能，说明影响文件、验证方式和回滚方式。
5. 读者选择一个功能后，让 Agent 创建任务、写 PRD，并记录真实验证命令。
6. 检查 `prd.md` 的 In scope、Out of scope、Acceptance criteria。
7. 让 Agent 进入实现；确认它没有自动提交、推送或越界改文件。
8. 运行质量检查，必须看到真实 lint/typecheck/test 结果。
9. 人工检查 diff、测试和验收条件。
10. 提交代码。
11. 运行平台提供的收尾入口，例如 `/omt:finish-work`；没有该命令时让 Agent 按 `finish-work` 技能执行。
12. 确认任务已归档、会话日志已写入，当前任务指针已清理。

### 5.4 首任务页面必须展示

- 每一步用户输入和 Agent 预期动作；
- 初始化成功后的目录树；
- 任务创建后 `task.json` 的关键字段；
- PRD 的最小示例；
- 验证通过和失败的输出示意；
- 归档前后的任务路径；
- 常见失败：平台未安装、Python 版本不对、任务状态未激活、验证命令不存在、提交前工作区不干净；
- 明确的“不安全示例”，例如不要在首任务做用户表迁移或支付逻辑。

### 5.5 计时口径

20 分钟从读者选定一个符合安全条件的业务功能后开始，不包含安装 Node.js/Python、克隆仓库或等待大型依赖安装。首次可用性测试需要至少 3 名未接触 omtre 的开发者，至少 2 名完成全部 12 步并能解释关键产物。

1. 使用场景；

固定顺序：

1. 快速索引；

4. 默认值和版本；
5. 平台或运行时限制；
6. 相关概念。

### 6.5 页面元数据

Markdown frontmatter 至少包含：

```yaml
---
title: 页面标题
description: 用于搜索和 SEO 的一句话
audience: first-time | team | advanced | contributor
maturity: stable | mixed | advanced | not-in-scope
since: 1.0.0
---
```

`maturity` 用于在页面顶部渲染状态标签，不能只写在正文里。

## 7. 写作规范

1. 中文正文使用第二人称“你”，一个段落只表达一个判断。
2. 中文首次出现术语时附英文原名和一句解释，例如“工作树（worktree）”。
3. 先写用户动作，再写机制解释。
4. 命令必须可复制；需要替换的变量用 `<your-name>` 形式。
5. 每个教程检查点必须是可观察的文件、状态或命令输出。
6. 解释区别时使用表格，例如“命令 vs 技能”“提交 vs 归档”“警告 vs 阻断”。
7. 禁止使用“完全自动”“保证跳过不了”“支持所有平台”“生产可用”等无法验证的绝对表述。
8. 平台差异必须具体到路径、hooks、子代理和验证状态。
9. 安全相关操作必须先给 `--dry-run`，再给实际命令。
10. 不复制上游文案；只复用信息组织方式和概念。
11. 每页必须有唯一标题、description、明确下一步。
12. 不创建空壳页面；未完成页面不进入导航，构建应失败。

### 7.1 统一状态标签

| 标签 | 含义 |
|---|---|
| 稳定可用 | 1.0.0 代码与自动化测试已覆盖 |
| 按平台而异 | 行为取决于宿主是否提供 hooks、子代理或命令原语 |
| 高级 / 需自理 | 功能存在，但依赖团队提供真实验证命令、权限、运维或安全审查 |
| 不在当前范围 | 产品明确未提供，不能用路线图口吻暗示已可用 |

标签组件渲染为带文字的徽标和说明块，不能只用颜色传达状态。

## 8. 视觉与阅读设计

### 8.1 品牌

- 沿用仓库现有 `assets/hero.svg`、工作流图与蓝绿色调。
- 使用文字字标 `omtre`；不引入新的商标、第三方图片或客户 Logo。
- 首页和文档页共用同一主题色、字体栈和代码高亮。
- 支持浅色和深色，二者对比度均满足正文可读性。

### 8.2 首页

1. 定位标题和一句话边界；
2. “完成第一个任务”主 CTA；
3. 安装命令复制块；
4. 三条入口卡：第一次使用、接入已有项目、团队评估；
5. 五阶段工作流图；
6. `.omtre/` 文件地图；
7. 能力与边界摘要；
8. 平台覆盖、文档资源和 GitHub/npm 入口。

不使用自动轮播、视差、持续动画和会遮挡正文的浮层。

### 8.3 文档页

- 左侧分组侧栏，当前页自动展开。
- 右侧页内目录只显示 H2/H3。
- 顶部面包屑，正文最大宽度约 760px。
- 代码块一键复制；平台差异使用标签页。
- 提示组件分为 note、tip、warning、danger。
- 表格支持横向滚动，不挤压手机正文。
- 每页底部提供编辑此页、最后更新、上一页/下一页。
- 移动端侧栏使用抽屉，正文最小宽度 360px。

### 8.4 无障碍

- 键盘可以打开/关闭搜索和移动端导航。
- 所有状态标签有文字，不依赖颜色。
- 焦点样式可见。
- 图片有中文 alt；装饰图使用空 alt。
- 正文标题层级连续，不跳级。

### 9.2 依赖与脚本

- 在根 `pnpm-workspace.yaml` 加入 `docs-site`。
- `docs-site/package.json` 使用仓库当前 pnpm 版本锁文件，VitePress 与 Mermaid 插件固定版本。
- 根脚本新增：

  ```json
  {
    "docs:dev": "pnpm --dir docs-site dev",
    "docs:build": "pnpm --dir docs-site build",
    "docs:verify": "pnpm --dir docs-site verify"
  }
  ```

- `verify` 依次执行 CLI 参考生成检查、临时仓库快速上手检查、VitePress 构建。
- 站点部署使用 Node 20，与主 CI 一致。
- 不引入 Algolia、SaaS 搜索、访问统计或远程字体。

### 9.3 配置

- `lang: zh-CN`。
- `base` 默认 `/omtre/`，适配 GitHub Pages 项目路径；内部链接禁止手写以 `/` 开头的站点绝对路径。
- `cleanUrls: false`，保留 `.html` 产物，避免 GitHub Pages 对无扩展名深链的兼容性差异。
- `lastUpdated: true`；CI checkout 使用完整历史。
- `head` 设置标题、description、Open Graph 和站点图标。
- 本地搜索开启，索引正文和标题。
- 内部死链由构建直接报错。
- 版本号从 `packages/cli/package.json` 读取并注入页头，不手写第二份版本真源。
- 生成 sitemap。

### 9.4 导航与搜索

- 顶部导航不超过 7 个入口。
- 侧栏数据集中在 `sidebar.mts`，页面不存在时构建失败。
- 搜索占位文案为“搜索命令、任务、平台或问题”。
- 搜索结果保留标题、层级和摘要，支持键盘选择。

### 9.5 图表

- 首页使用现有 SVG 素材。
- 运行时生命周期、任务产物关系、Channel 事件流使用 Mermaid。
- 每张图下方提供一段等价文字说明，不能只靠图传达关键信息。

## 10. 内容防漂移

### 10.1 CLI 参考

- `generate-cli-reference.mjs` 调用已构建 CLI 的 `--help` 输出，生成 `/reference/cli` 的参数部分。
- 生成文件提交到仓库；CI 重新生成后执行 `git diff --exit-code`，参数变化但文档未更新时失败。
- 页面的人工说明放在同目录的静态片段或模板中，不覆盖生成的参数表。
- `release:check` 或发布 workflow 增加文档版本、构建和 CLI 参考检查。

### 10.2 文件与 Schema 参考

- 每个参考页顶部标注“适用版本 1.0.0”和来源文件。
- `task.json`、JSONL、目录树字段必须从当前模板和脚本核对。
- 上游变化不等于 omtre 行为；不得直接同步上游参考页。

### 10.3 快速上手验证

`verify-quickstart.mjs` 在系统临时目录：

1. 创建临时 Git 仓库和开发者身份；
2. 使用已构建 CLI 执行 `init`；
3. 断言 `.omtre/workflow.md`、脚本、任务目录和平台目录存在；
4. 创建任务并断言 `task.json` 状态；
5. 写入一个验证命令并确认任务验证状态流转；
6. 归档并确认目录移动；
7. 清理临时目录。

该脚本只验证 CLI 与脚本闭环，不模拟真实模型对话；Agent 交互、人工检查和业务功能完成度保留真人验收。

### 10.4 文档测试

- VitePress build 失败即阻止合并。
- 内部链接和侧栏目标必须存在。
- 关键命令块由脚本或人工检查与 `--help` 一致。
- 每次发布前重新运行快速上手指南验证。
- 新增或修改 CLI 选项、配置字段、平台路径时，同一 PR 必须更新相关文档或明确说明不适用。

## 11. GitHub Pages 发布

### 11.1 `docs.yml`

触发：

- `pull_request`：只构建和验证；
- `push` 到 `main`：构建、验证并部署；
- `workflow_dispatch`：手动重跑。

PR 作业权限：

```yaml
permissions:
  contents: read
```

部署作业权限：

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

步骤：

1. checkout（完整历史用于最后更新时间）；
2. setup Node 20 与 pnpm；
3. `pnpm install --frozen-lockfile`；
4. `pnpm build`；
5. `pnpm --filter omtre lint:py`；
6. `pnpm docs:verify`；
7. 上传 `docs-site/.vitepress/dist`；
8. 仅 main 分支部署 GitHub Pages。

设置 concurrency，避免旧部署覆盖新部署。

### 11.2 URL

首版地址：

```text
https://scofan-official.github.io/omtre/
```

自定义域名不在本设计范围。若后续绑定，只改 `base`、站点 URL 和仓库 Pages 配置，不改正文链接。

### 11.3 发布后检查

- 首页、五个导航入口和搜索可用。
- 直接访问深链不会 404。
- 手机宽度无横向溢出。
- 浅色/深色、键盘导航可用。

- `llms.txt` 和 sitemap 可访问。

## 12. 文档维护边界

- `docs-site/` 是面向用户的唯一真源。
- 根 `README.md` 只保留定位、最短安装路径和指向文档站的入口，不再重复完整教程。
- `docs/design.md`、`docs/release.md`、`docs/upstream.md` 继续服务维护者。
- `docs/pack.md` 中的用户说明迁入资源页后改为指向站点；历史内容在确认后再处理，不在首版擅自删除。
- 文档变更像代码一样经过 PR review。
- 术语以仓库 `GLOSSARY.md` 为准；没有收录的术语在首次出现处定义。
- 规范模板或平台适配变化必须检查对应页面和平台矩阵。
- 每次 CLI 发布前必须通过文档构建、链接检查和快速上手脚本。
- 真人可用性测试在首版发布前完成一次，之后每次大改首任务路径时重跑。

## 16. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 完整对标范围过大 | 正文长期不完整 | 以阶段 2 上手闭环为硬门槛，再扩进阶 |
| 文档与 CLI 漂移 | 用户执行失败 | 生成 CLI 参考，CI 检查 diff |
| 教程绑定单一语言或框架 | 多数读者无法复现 | 首任务用候选筛选和通用检查点，不硬编码业务代码 |
| 继续沿用宣传性描述 | 预期落差和现场质疑 | 状态标签、能力矩阵、内容评审对照 1.0.0 行为 |
| 平台文件生成被误写为完整支持 | 用户在未验证平台踩坑 | 平台页分别标注注入方式与验证深度 |
| GitHub Pages 子路径断链 | 部署后导航失效 | 统一 `base`，PR 构建即检查 |
| 搜索质量不足 | 找不到命令或概念 | 维护同义词、页面 description，发布前做任务式搜索测试 |
| 文档数量增长后难维护 | 重复和过期 | 单一真源、四类模板、生成参考、发布前检查 |
| 真人测试暴露上手失败 | 首版延期 | 阶段 2 优先修路径，不把失败归因于用户 |

## 18. 术语

| 术语 | 本文含义 |
|---|---|
| 任务（task） | `.omtre/tasks/` 下的一个可计划、实现、检查和归档的工作单元 |
| 规范（spec） | `.omtre/spec/` 下供 Agent 在编码前读取的项目规则 |
| 技能（skill） | 由宿主按意图加载的工作流指令包 |
| 子代理（sub-agent） | 由主会话派发的独立 Agent，承担 research、implement 或 check |
| 工作树（worktree） | `omtre run` 为单个任务创建的独立 Git 工作目录 |
| 验证契约（verify contract） | 任务中登记、可由脚本重放的真实检查命令 |
| 消融（ablate） | 临时移除项目内 omtre 表面并保留外部恢复事务 |
| 首任务 | 新读者完成的第一个真实业务小功能 |
