# 项目记忆与日志

<MaturityBadge level="stable" />

omtre 的项目记忆并非依赖大语言模型不可见、不可控的隐式记忆向量，而是建立在仓库版本控制之上的结构化会话日志与元数据。它确保 Agent 在跨会话恢复时能够快速建立历史上下文，并为人类工程师复盘技术取舍提供同源证据。

## 架构边界与隔离模型

omtre 将本地与协作状态严格划分为两类：**个人本地状态**与**团队共享事实**。

```text
.omtre/
├── .developer                    # [本地独占/忽略] 当前 checkout 绑定的开发者标识
├── .runtime/                     # [本地独占/忽略] 会话指针、活跃任务与运行时流水
├── spec/                         # [团队共享/跟踪] 权威工程规范与架构契约
├── tasks/                        # [团队共享/跟踪] 活动与归档任务、PRD、验证契约
└── workspace/
    ├── index.md                  # [团队共享/跟踪] 团队工作区开发者导航索引
    └── <developer>/              # [团队共享/跟踪] 该开发者专属的历史工作区
        ├── index.md              # 个人会话历史时间线索引
        └── journal-N.md          # 个人结构化会话流水
```

状态分类与归属矩阵：

| 路径分类 | Git 状态 | 生命周期与定位 | 冲突风险 |
|---|---|---|---|
| `.omtre/.developer` | 忽略（.gitignore） | 本机身份标记。决定日志与 `--mine` 过滤使用的开发者名。 | 无 |
| `.omtre/.runtime/` | 忽略（.gitignore） | 本机瞬态。记录当前活动任务指针、执行进程 PID 与临时锁。 | 无 |
| `.omtre/spec/**` | 提交跟踪 | 团队共享的规范与设计约定。 | PR 评审冲突 |
| `.omtre/tasks/**` | 提交跟踪 | 业务需求与工程交付容器。按任务目录隔离。 | 同任务并行修改冲突 |
| `.omtre/workspace/<dev>/**` | 提交跟踪 | 开发者个人维度的工程日志与决策上下文。 | journal 使用 union merge；`index.md` 仍可能冲突 |

## 开发者身份与并行写入

团队协作中，多个开发者和多个 Agent 实例常常在各自的分支上并行开展任务并产出日志。

### `.omtre/.developer` 的核心职能

在项目初始化或新成员加入时，通过标识参数生成 `.omtre/.developer`：

```bash
# 初始化个人开发者身份，例如 scofan
omtre init -u scofan --qoder
```

该文件只包含开发者名和初始化时间，并被 `.gitignore` 忽略。它用于：

1. **确定写入路由**：`add_session.py`、`task.py list --mine` 等工具读取这个本地标识，定位 `.omtre/workspace/<developer>/` 并计算归属。
2. **避免身份漂移**：日志路径按开发者名分开，正常情况下不会写到别人的工作区；但 Git 合并仍可能让同一目录产生冲突。

它不是登录凭据，不参与鉴权、权限判断或远端身份校验。

### 并行提交的冲突边界

传统团队日志方案通常采用单一的共享日志文件（如根目录下的 `CHANGELOG.md` 或全局 `log.md`），多人同时在不同分支追加内容会导致 Git rebase/merge 时频繁触发文件尾部冲突。

omtre 按开发者拆分目录，并给 `journal-*.md` 配置 `merge=union`，因此常见的新增日志冲突会减少。它不提供“零冲突”保证：

- 同一开发者的多个 checkout 仍可能同时写同一 journal；
- `.omtre/workspace/index.md` 不在 union merge 规则内，发生冲突时需要人工合并；
- 任务目录或用户手工重排日志仍可能产生结构性冲突。

## 会话日志（Journal）的记录边界

会话日志的目的是为未来的自己、接手的队友以及后续会话中的 Agent 还原技术脉络。信噪比决定了日志的实用寿命。

### 应该记录什么

一条高价值的 journal 条目聚焦于**代码变更背后的元信息**：

- **关键决策与方案选型（Why）**：为什么选择了方案 A 而放弃方案 B；为什么引入新的数据结构或依赖。
- **技术妥协与已知限制（Trade-offs）**：为了满足发布时间点所做的临时性折中；明确记录后续需要补齐的技术债务。
- **排障与根本原因（Root Cause）**：排查耗时严重的隐蔽 Bug 现场；第三方库的未记录行为（Undocumented behavior）及规避方式。
- **验证证据与提交锚点**：关联的任务路径、通过的测试用例与确定性的 Git Commit Hash。

### 严禁记录什么

必须坚决避免将 journal 变成垃圾场：

- **严禁粘贴大段代码 Diff**：代码本身已由 Git 精准记录。在 Markdown 中重复粘贴代码只会浪费大模型上下文窗口，且在代码演进后形成具有误导性的过期副本。
- **严禁转储冗长的终端执行输出**：完整的 `npm install` 输出、长篇 Traceback 或海量静态检查警告应在修复后丢弃，仅需在日志中简明提炼关键问题与根因结论。
- **严禁保存完整模型聊天流水**：不要把“你好”、“请帮我分析”等对话问答直接倾倒进日志。
- **严禁写入敏感机密数据**：包括但不限于 API Keys、Token、私钥证书、密码及未脱敏的生产环境客户数据。

## 会话收尾与日志写入机制

标准收尾操作通常由 Agent 在完成任务后自动化触发，或由工程师通过脚本执行：

```bash
python3 .omtre/scripts/add_session.py \
  --title "Add order status filter" \
  --commit 8f3b21a \
  --change "新增 status 参数解析与枚举校验逻辑" \
  --test "pnpm test:unit 通过，覆盖无效状态码 400 分支" \
  --next-step "等待前端组件适配并联合验收"
```

写入行为会先校验提交及索引结构：

- **默认并非全自动幂等**：重复执行同一条 `add_session.py` 请求可能新增一条日志。自动化调用应传入 `--idempotency-key`，让已提交的相同请求成为 no-op，而不是重复追加。
- **提交证据校验**：传入的 `--commit` 必须能在本地 Git 数据库中解析为真实提交对象，阻止虚构无效的日志记录。
- **行数阈值轮转**：单个 `journal-N.md` 达到 `max_journal_lines`（默认 2000 行）时，脚本会自动创建新的 `journal-(N+1).md`，防止超大文件拖慢编辑器和模型检索性能。

## 跨会话恢复机制

新会话启动或切换分支时，Agent 按照以下确定性顺序重建工作现场：

1. **读取本地开发者标记**：通过 `.omtre/.developer` 确定当前操作者名与日志目录。
2. **检索近期 Journal**：读取 `.omtre/workspace/<developer>/index.md` 中最近 1~2 次的会话摘要，了解上次中断时的进展与遗留待办。
3. **定位活跃任务**：通过 `task.py current --source` 获取当前绑定的任务目录，加载 `prd.md` 和 `design.md`。
4. **校准 Git 分支**：核对当前工作区分支与任务声明的分支是否一致。

只要日志中如实记录了关键结论和提交锚点，新会话通常能较快恢复工作，减少工程师重复讲解背景的成本。
