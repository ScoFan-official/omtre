# FAQ

<MaturityBadge level="mixed" />

## 安装与依赖

### 必须全局安装吗？

默认安装方式是：

```bash
npm install -g omtre
```

也可以使用项目约定的版本管理或内部镜像。团队应先固定版本，不要每个成员自行跟随 latest。

### 为什么还需要 Python？

`.omtre/scripts/` 下的任务、验证、上下文和收尾脚本主要是 Python。核心要求是 Python 3.9+。hooks 使用的解释器可能与终端不同，排障时要单独检查。

### 能在 Windows 上使用吗？

可以，但当前 CI 以 Linux 为主。Windows 需要实际验证路径、Python 命令、hooks 和子代理流程。不要仅凭文件生成成功判断平台完整可用。

### 安装后为什么命令找不到？

检查 npm 全局 bin 是否在 PATH，重新打开终端，再运行：

```bash
npm bin -g
omtre --version
```

不同 npm 版本的全局 bin 命令可能不同，也可以直接检查 `npm config get prefix`。

## 任务与流程

### omtre 会自动创建任务吗？

不会机械决定。Agent 根据工作流分类请求，复杂任务应先询问用户是否创建。小问题可以跳过任务。

### `start` 是不是实现开始？

`task.py start` 把任务从 `planning` 改为 `in_progress`，并写会话指针。它是计划审查后的阶段门槛，不负责启动代码生成。

### `finish` 和 `finish-work` 有什么区别？

- `task.py finish`：清除当前会话的活动任务指针，不归档；
- `finish-work`：收尾流程，归档任务并记录 journal。

### 代码没提交能归档吗？

**不要这样做。** 归档脚本本身不检查工作区是否还有未提交业务代码，但团队流程应固定为：
1. `git commit` 是业务实现的入库动作，必须由工程师显式检查 diff；
2. `task.py archive` 负责状态归档、验证重放和任务簿记；
3. 若未提交代码便先行归档，任务目录移动会与业务修改混在同一工作区，增加审查和回滚难度。

### 收尾会自动 push 代码吗？

**原生归档脚本（`task.py archive`）绝对不会执行 git push。** 何时将分支推送到远端、何时创建 PR，主权完全掌握在开发者手中。若宿主中的复合自定义命令（如某些自带的 finish-work 命令）包含推送行为，请在向 Agent 发出收尾指令时明确追加：“先不要 push”。

### `task.py current` 提示没有任务怎么办？

排查路径：
1. 确认当前分支是否运行过 `task.py create`；
2. `task.py create` 在能解析会话标识时会直接绑定当前任务；如果创建时使用了 `--no-start`，则不会绑定；
3. `task.py start <task-dir>` 会把 `planning` 翻转为 `in_progress`，并再次尝试写入当前任务指针；
4. 检查当前会话是否提供 `OMTRE_CONTEXT_ID` 或平台原生 session id。没有会话标识时，`start` 仍可能翻转状态，但不会持久化当前任务指针。`.omtre/.developer` 只影响日志目录和 `--mine` 过滤，不是鉴权凭据。

## 规范与验证

### 规范是不是越多越好？

**不是。** 规范堆砌是严重的负优化：
- 凡是能被 ESLint、Prettier、TypeScript 或单测机械阻断的语法与风格规则，坚决不写进 Prompt 规范；
- 规范文件只应承载分层架构约定、核心领域数据契约与架构妥协背景；
- 无法通过代码审查进行客观判断的规则，只会稀释大模型的注意力并增加上下文 Token 浪费。

### Agent 会自动无条件遵守所有规范吗？

**不会。** 规范加载本质上是向大模型窗口注入参考上下文（Soft Guidance），绝不是操作系统级的安全沙箱。只有本地脚本结合退出码机械判定的条件才是硬闸门，例如任务存在验证契约且未显式跳过时，验证失败会阻止归档。生产环境的最终安全防线仍由人工审查和 CI/CD 承担。

### 验证契约是不是 CI 的替代品？

**不是。** 验证契约是开发者在本地环境绑定的可复现检验清单，用于在任务归档前提供第一道机械门禁。它不能替代干净容器环境中的全局 CI 构建、跨服务集成测试、依赖扫描与分支保护策略。

### 没有测试可以跳过验证吗？

项目若配置了 `verify_required: true`，缺少验证命令将无法正常归档。脚本支持 `--skip-verify "<reason>"` 显式跳过：原因必须非空，并会作为 `verify_skipped` 写入 `task.json`。对于没有自动化测试的仓库，首要任务是在项目中建立最小测试脚手架，而不是将跳过验证变为常规操作。

### 验证失败但改动极小，可以直接归档吗？

**严禁盲目放行。** 验证契约失败意味着本地子进程返回了非 0 退出码（如单测挂起或类型报错）。即使改动仅有单行，测试失败通常揭示了深层的破坏性断言或潜在回归。必须先排查修复测试，保证退出码为 0 后再归档。

## 平台

### “支持 22 个平台”是什么意思？

omtre 生成 22 个平台的文件集合。宿主是否提供 hooks、命令或子代理，以及宿主版本是否真的工作，需要分别验证。见[平台支持矩阵](./platform-matrix.md)。

### 我应该同时初始化多个平台吗？

团队有多种工具时可以，但建议先在 1–2 个平台完成真实闭环。多平台会增加 hooks、命令语法和排障路径。

### 为什么我的平台没有 SessionStart？

不是所有宿主都提供同样的生命周期能力。有的使用 prompt hook，有的依赖子代理自行读取，有的需要显式命令。

### 为什么 `.claude/`、`.qoder/` 等文件会被更新？

这些是受管平台文件。使用 `omtre update --dry-run` 查看变更。自定义内容应放在未被管理的独立文件中。

## 升级与生命周期

### `omtre upgrade` 和 `omtre update` 的本质区别？

- **`omtre upgrade`（或 `npm i -g omtre`）**：升级本机全局 CLI。`omtre upgrade` 会解析 GitHub `cli-v*` release 并安装对应 tgz；它不修改项目仓库；
- **`omtre update`**：项目维度的同步，将受管脚本、工作流和平台文件更新到本机 CLI 的版本。冲突需要按提示保留、跳过或生成 `.new`，它不提供自动三方合并。

### 升级覆盖了我的定制怎么办？

首先通过 `git checkout` 或 `git diff` 从版本控制中找回。在执行 `omtre update` 前，务必先通过 `--dry-run` 审查变更清单；对于定制程度较高的规范，推荐使用 `--create-new` 参数将新模板输出为 `.new` 文件，再由人工手动比对合并，切勿日常滥用 `--force`。

### ablate（临时消融）和 uninstall（卸载）的区别？

- **`omtre ablate`**：临时移出项目受管文件，并在项目外的 `~/.omtre/ablations/` 创建恢复事务，可通过 `omtre restore` 还原，**不是卸载**；
- **`omtre uninstall`**：永久删除当前项目内的 `.omtre/` 及平台适配目录，但保留全局 CLI 二进制。

若仅需排查 Hook 运行异常，无需消融或卸载，只需在终端执行 `export OMTRE_HOOKS=0` 关闭 omtre hooks；宿主自身的其它 hooks 不受此变量控制。

### 临时消融后还能恢复吗？

可以，前提是恢复事务仍然存在，并且消融期间受管路径没有被改到冲突。先运行 `omtre restore --dry-run`。

## 数据与安全

### workspace 日志会提交到 Git 吗？

默认模型通常提交，因为它是跨会话记忆的一部分。具体以项目的 `.gitignore` 和收尾策略为准。

journal 不自动脱敏，不要在日志里放密钥、客户隐私或生产凭证。

### omtre 会把代码上传到云端吗？

omtre 本身不托管代码或任务状态。平台文件、任务、规范和日志都在仓库。Channel 的存储也是本机文件。

但你选择的 AI 宿主、模型提供商和 MCP 仍可能把上下文发送到其服务，需单独评估。

### Channel 可以多人跨机器使用吗？

1.0.0 的 Channel 是本机事件日志和本地 worker 协作，不是带认证、权限和云端存储的多用户服务。`by` 是显示别名，不是身份认证。

### `omtre run` 会自动合并 PR 吗？

不会。它可能在交付门允许时 push 任务分支并创建 ready PR，但不会 merge，也不应推送默认分支或 tag。

## 团队接入

### 最小试点应该怎么做？

- 一个非关键仓库；
- 3–5 名成员；
- 1–2 个实际平台；
- 一个低风险业务闭环；
- 人工提交和 Review；
- `verify_required: true`；
- 两周后看收益与维护成本。

### 必须维护大量规范吗？

不需要。先写当前任务真正使用、能从代码或评审反馈证明的规则。

### 什么情况下不该引入？

- 团队只需要一个简单规则文件；
- 没有测试、审查和提交边界；
- 首个试点只能做高风险改动；
- 期望无人值守全自动交付；
- 无法接受仓库内任务和日志带来的维护成本。
