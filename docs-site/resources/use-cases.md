# 使用案例

<MaturityBadge level="stable" />

这里只列可核验的 omtre 自用案例，不虚构客户 Logo、效率提升百分比或未公开项目。

## 案例 1：用 omtre 管理 omtre 自身

### 背景

omtre 从上游工作流项目演进为独立产品线。仓库本身使用 `.omtre/` 管理规范、任务、workspace 和代理角色，同时也包含 CLI 与核心库。

### 做法

- 规格按包/层放入 `.omtre/spec/`；
- 每个变更使用任务目录记录 PRD、计划与检查；
- Python 项目脚本和 TypeScript CLI 在同一仓库维护；
- 收尾写入开发者 journal；
- 发布走独立 `cli-v*` tag 和 CI。

### 可观察证据

- 根目录存在完整的 `.omtre/`；
- 大量任务归档位于 `.omtre/tasks/archive/`；
- 多开发者 journal 位于 `.omtre/workspace/`；
- CI 运行 lint、类型检查、构建和测试；
- 文档站源码位于 `docs-site/`。

### 可借鉴点

- 不要只把框架用于“别的项目”，维护者自己首先要能承受这套流程；
- 规范、任务和脚本要与产品代码一起审查；
- 文档站应与 CLI 版本绑定，避免宣传和行为脱节。

### 不要照搬

- 仓库历史包含上游时期任务，不代表独立 1.0.0 的全部实践；
- 自用深度不等于外部大规模采用；
- 维护者熟悉内部机制，不能据此低估新人的学习成本。

## 案例 2：上游项目到 omtre 的一次性迁移

### 背景

omtre 早期项目结构来自上游 0.6.x。独立命名的同时，需要让已有项目能安全迁移。

### 做法

- 提供 `omtre migrate --dry-run` 预检；
- 检查工作区、版本、活动进程和目录冲突；
- 迁移任务、规范、workspace、domains 和自定义平台文件；
- 对修改过的受管文件写 `.backup`；
- 跑迁移后自检；
- 明确不会自动回滚，Git 和外部备份是恢复手段。

### 可借鉴点

- 结构迁移先做计划，再做写入；
- 用户数据与受管文件分开处理；
- 迁移后必须用真实任务验证，而不是只看目录改名；
- 不同迁移/升级/恢复语义必须分开命名。

## 案例 3：在仓库内固化“检查证据”

### 背景

AI 会话很容易给出“已完成”的总结，但没有可重放证据。

### 做法

- 将 lint、typecheck、test 登记为任务验证契约；
- 归档前重新运行；
- 失败阻止归档；
- 无契约时由 `verify_required` 决定是否阻断；
- 提交与归档分成不同提交单元。

### 可借鉴点

- 用退出码而非自然语言总结作为最低证据；
- 验证命令必须能在干净环境运行；
- 不把本地验证当 CI 替代；
- 允许跳过，但必须留原因并 Review。

## 案例 4：多平台共用一套项目状态

### 背景

团队成员使用不同 AI 宿主，但需要共享项目规范和任务边界。

### 做法

- 核心状态统一放在 `.omtre/`；
- 每个平台只生成自己的 commands/skills/agents/hooks；
- 上下文由 hook 注入或子代理自读；
- 平台差异写入支持矩阵；
- 先从实际使用的少数平台试点。

### 可借鉴点

- 统一的是事实层，不是所有宿主的交互方式；
- “生成了文件”不等于“宿主端验证”；
- 平台升级后重新验证 hooks 和子代理；
- 不要求团队为了工具统一而更换编辑器。

## 如何评估你自己的案例

如果准备在团队内分享 omtre 案例，请记录：

- 项目类型和团队规模；
- 使用的平台与版本；
- 试点任务类型；
- 完成时间；
- 验证与 Review 证据；
- 失败和绕过情况；
- 维护成本；
- 是否继续使用。

只分享“感觉更快”没有决策价值。
