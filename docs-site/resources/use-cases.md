# 使用案例

<MaturityBadge level="stable" />

本篇汇总 omtre 在实际工程研发中经过长期验证的技术落地模式，全部基于**可公开审计的 Git 历史记录、真实任务工单与自动化 CI 门禁证据**，绝不罗列虚构的商业宣传案例或未公开指标。

## 案例 1：基于 omtre 研发与演进 omtre 自身（Dogfooding 自举）

### 工程背景
omtre 作为一个独立的 Agent Workflow Harness，其自身的代码库（包含 TypeScript CLI、`@omtre/core` SDK、Python 原生运行脚本与文档站）全面采用 `.omtre/` 进行日常研发管理。

### 核心落地实践
- **分层规范约束**：在 `.omtre/spec/` 中分别固化了 CLI 模块、后端状态机、单元测试策略与文档站技术写作红线；
- **任务驱动演进**：所有需求变更均在 `.omtre/tasks/` 下建立原子工单，严密记录 PRD、架构设计方案与验证命令；
- **会话留痕与多开发者协同**：团队成员在各自的 `workspace/<name>/journal-N.md` 中记录实施决策与排障流水；journal 使用 union merge，`index.md` 等索引文件仍可能需要人工解决冲突；
- **全量自动化守门**：发布前必须通过 CI 全矩阵检验（包含代码构建、单元测试、死链检查与真实快速开始端到端黑盒流转）。

### 关键工程启示
- **自举是最好的成熟度检验**：若工作流 harness 的维护者自己都无法在日常开发中承受其流程约束，该方案在其他团队中必然失败；
- **文档与代码同仓维护**：文档站在 `docs-site/` 中随代码一起审查；部署由独立 Docs workflow 触发，因此“同仓”不等于与 CLI 二进制原子发布；
- **清醒评估引入成本**：维护者对内部机制的熟悉，不代表团队新成员可以免除学习成本，必须建立清晰的入门演练路径。

## 案例 2：从上游历史架构一次性无损迁移

### 工程背景
随着 omtre 演变为具备独立版本线与设计准则的产品，需要为原有的上游 0.6.x 存量项目提供可预检、可备份、可审计的迁移路径。这里的“无损”以迁移前 Git 提交和外部备份为前提，不是迁移脚本自动回滚的保证。

### 核心落地实践
- **预检先行（Dry-run Preflight）**：通过 `omtre migrate --dry-run` 严格检查工作区状态、活动进程句柄与潜在路径冲突，杜绝盲目写入；
- **受管文件与用户数据严格隔离**：对用户手工定制过的平台文件自动生成 `.backup` 副本，绝不强行重命名任务目录；
- **自检与外部物理备份兜底**：明确迁移工具自检失败绝不自动回滚，要求开发者必须在代码库外部建立物理冷备份，依靠 Git 还原基线。

### 关键工程启示
- 大型架构与命名空间迁移必须遵循“先算后写、无损备份、严格自检”的防御性编程原则；
- 架构迁移（`migrate`）与日常小版本升级（`upgrade`/`update`）必须在语义与命令上严格拆分，避免操作认知混淆。

## 案例 3：以机器退出码替代自然语言口头保证

### 工程背景
在大模型辅助编程中，Agent 极易在对话中给出“所有代码已修改完毕并通过测试”的口头总结，但实际可能存在编译报错或漏跑断言。

### 核心落地实践
- **固化本地验证契约**：将 `pnpm lint`、`pnpm typecheck`、`pnpm test` 等非交互命令持久化登记进任务的 `task.json.verify`；
- **归档时重放验证**：`task.py archive` 在任务存在验证契约且未跳过时，重新执行命令并检查退出码；
- **显式审计追踪**：确需跳过时使用 `--skip-verify "<reason>"`，原因会写入 `task.json.verify_skipped`，供后续 Code Review 审计。

### 关键工程启示
- **退出码是最低的工程底线**：大模型的自然语言承诺不可作为交付依据，只有机器可执行、可复现的 Exit Code 0 才是坚实的事实；
- 验证契约不能替代 CI，但能在代码离开开发者本地机器前筑牢第一道拦截网。

## 案例 4：单一仓库状态轴支持多 IDE 混用协作

### 工程背景
现代研发团队中，不同成员日常使用的 AI 编码工具有所不同（如部分工程师使用 Cursor，另一些使用 Claude Code 或 Qoder），传统模式下各工具的规则配置割裂严重。

### 核心落地实践
- **单一事实主轴**：将团队规范、任务需求与日志统一沉淀在 `.omtre/` 核心目录中；
- **宿主薄适配层**：根据成员实际使用的工具，分别生成 `.claude/`、`.cursor/`、`.qoder/` 等专用配置文件；
- **统一生命周期**：各平台虽然派发子代理或 Hook 调用的通道不同，但底层读写的是同一份 `task.json` 状态机。

### 关键工程启示
- 研发团队无需为了引入 AI 规范而强制所有人更换代码编辑器；
- 规范统一的是仓库内的工程事实，而不是强行统一上层交互界面。

## 团队自身试点案例评估框架

在团队内部评估是否长期采纳 omtre 时，应基于以下客观指标进行量化记录，切忌以主观的“感觉变快了”作为决策依据：

- **变更边界控制率**：每次任务修改的文件数量是否被严格限制在 PRD 范围内（杜绝随意扩散修改）；
- **验证契约覆盖率**：归档的任务中，具备 Exit Code 0 机器验证证据的比例；
- **单分支回滚成功率**：发生线上缺陷时，能否直接通过单个任务分支干净回滚；
- **规范冲突与维护耗时**：团队每周在维护 `.omtre/spec/` 与审查规范上实际花费的人工时间。
