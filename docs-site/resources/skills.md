# Skills

<MaturityBadge level="mixed" />

技能（Skill）是 omtre 体系中可复用的工程工作流与专家方法论封装。技能向 Agent 注入特定任务的推进步骤与审查准则，作为可选能力按需挂载，**绝非安装 omtre 后必须无脑全量启用的常驻运行时**。

## 核心内置技能与推荐起点

在日常研发中，优先使用 omtre 标准工作流内置的阶段驱动能力，即可满足绝大多数任务闭环：

- `omtre-brainstorm`：计划阶段澄清模糊需求、补齐边界与验收条件
- `omtre-before-dev`：编码前根据任务上下文定向检索并装载相关领域规范
- `omtre-check`：实现完成后对照 PRD 验收标准进行多维度审查与命令重放
- `omtre-update-spec`：任务收尾前将经代码验证的高价值架构模式反哺回规范库
- `omtre-break-loop`：陷入连续调试失败或复杂死循环时强制中断试错并启动根因排查

::: tip 演进建议：从零起步，按需递增
首次接入切忌一次性复制全部市场技能。建议在团队遇到具体的研发痛点（如需要标准化编写 TDD 用例、重构老旧模块）时，针对性引入单个技能，观察效果后再沉淀入团队白名单。
:::

## 常见工程任务与技能匹配

| 工程场景 | 推荐技能标识 | 解决的核心问题 |
|---|---|---|
| **模糊需求推演** | `grilling`、`grill-with-docs` | 追问隐含业务假设，挖掘边界条件与技术盲区 |
| **讨论成果固化** | `to-spec` | 将聊天上下文整理为规范草案或架构决策记录 |
| **大型任务拆解** | `to-tickets` | 将宏观需求拆解为可独立回滚、具备验证契约的原子任务 |
| **测试驱动开发** | `tdd` | 严格按“红 - 绿 - 重构”小步快跑推进逻辑实现 |
| **顽固缺陷排查** | `diagnosing-bugs` | 收集现场日志、隔离环境干扰并构建最小复现用例 |
| **模块架构设计** | `codebase-design` | 梳理跨层依赖拓扑，定义数据模型与模块接口契约 |
| **前置技术调研** | `research` | 只读分析调用链与现有实现，产出结构化技术方案 |
| **代码交付审查** | `code-review` | 针对 Git Diff 核查架构破坏性、安全漏洞与测试完整性 |
| **UI 前端打磨** | `impeccable` | 对照设计系统审查组件封装、响应式断点与无障碍体验 |
| **工作交接导出** | `handoff` | 提取当前任务的未竟事项、排障记录与后续实施切片 |
| **编写高质量 PR** | `pr` | 提炼代码变更背景、改动范围、回滚方案与测试通过证据 |

具体可用的技能集合以安装目录与技能 Markdown 内部的 Frontmatter 为准。

## 技能安装与管理

```bash
# 为当前主力宿主（如 Qoder）复制指定技能包
npx skills add ScoFan-official/omtre --agent qoder --copy
```

安装前的准入核验：
1. **核验宿主兼容性**：确认技能格式是否被当前编辑器原生支持（如 Qoder、Claude Code、Cursor）；
2. **锁定发布版本**：指定 Git Tag 或 Commit SHA，切勿直接拉取未冻结的主干开发分支；
3. **先在练习仓库实测**：严禁未经代码审查直接向生产主干仓库批量引入第三方技能。

## 技能触发机制与上下文膨胀风险

技能在宿主中的生效机制通常分为两类：
- **语义自动匹配（Semantic Trigger）**：宿主将可用技能的 `name` 与 `description` 常驻注入大模型系统提示词，由模型在解析用户输入时自行匹配调用；
- **显式定向调用（Explicit Invocation）**：由开发者在对话中直接输入斜杠命令或自然语言指名调起。

::: danger 警惕全量安装导致的意图漂移与 Token 浪费
全量安装技能是严重的工程负优化：
1. **提示词上下文被大量挤占**：数十个技能的元数据会常驻占用上万 Token 的基础上下文预算，极大挤占代码阅读空间；
2. **意图竞争与误触发**：当存在大量描述相似的“审查”、“重构”技能时，大模型在推理时极易产生工具匹配歧义，导致在错误时机误调用；
3. **维护成本陡增**：团队难以辨识代码究竟是在哪套规则指导下生成的。
:::

## 技能与规范（Spec）的职责解耦

必须清楚区分技能与规范的物理定位，严禁混淆：

```text
┌────────────────────────────────────────────────────────┐
│ 技能（Skill）: 方法论与过程标准 (教 Agent "怎么做")     │
│ · 如何编写高质量 TDD 单测用例                          │
│ · 如何进行根因推演与日志隔离分析                       │
├────────────────────────────────────────────────────────┤
│ 规范（Spec）: 项目事实与架构契约 (约束代码 "应该怎样") │
│ · 本项目的测试目录拓扑、Fixture 目录与命名规约          │
│ · 核心接口错误码定义与数据库迁移约束                   │
├────────────────────────────────────────────────────────┤
│ 验证契约（Contract）: 机器退出码硬门禁 (判定 "是否完成") │
│ · pnpm test:unit 进程退出码必须为 0                    │
└────────────────────────────────────────────────────────┘
```

**核心铁律**：严禁把项目特有的路径与架构规约埋入通用技能中。项目专属事实必须存放于 `.omtre/spec/`，随代码版本一同演进。

## 技能安全审查准则

由于第三方技能正文可能包含指导 Agent 执行 Shell 脚本或访问网络的指令，引入前必须由工程师审查：
- [ ] 技能是否包含执行破坏性终端命令的引导（如未确认的删除、全局重命名）；
- [ ] 技能是否要求读取敏感凭据（API Keys、Token、私钥文件）；
- [ ] 技能是否强行发起非授权的外部网络请求；
- [ ] 技能是否包含未经审计的二进制可执行文件或外部脚本包装。

## 移除不用的技能

当某个技能不再适用于团队流程时，直接删除对应平台目录下的技能目录（如 `.qoder/skills/<skill-name>/SKILL.md` 所在的目录）。清理后重新在 IDE 中拉起新会话，确认大模型的可用工具列表中已不再展示该技能。
