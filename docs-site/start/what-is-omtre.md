# 认识 omtre

<MaturityBadge level="stable" />

omtre 是一套**面向 AI 编码代理的仓库内工作流框架（workflow harness）**。它不提供模型，也不替代你的编辑器，核心目标是将“这次要做什么、应该怎么做、做过什么”从不可追溯的聊天记录中剥离，沉淀为 Git 仓库内受控的工程事实。让 Agent 每次进入项目时，都从同一份规范、任务与上下文开始工作。

## 它解决什么问题

AI 编码代理通常不缺代码生成能力，但单次会话极度缺乏对长期工程事实的记忆与约束：

- **上下文随会话蒸发**：新会话既不清楚历史架构妥协，也记不住刚刚修复并验证过的踩坑细节；
- **多 Agent 隐式约定割裂**：团队成员分别在 Cursor、Claude Code、Codex 等工具中各写各的 Prompt，隐式约定无法在代码库中共享沉淀；
- **交付缺乏客观证据**：代码审查只能对着一堆散乱 diff 凭空猜测意图，缺乏变更边界（PRD）、设计依据与可重放的真实验证记录。

omtre 的解决思路不是指望大模型“记忆力变好”，而是让所有关键事实落盘到 Git 受控文件中：

| 你想保留的内容 | omtre 中的位置 |
|---|---|
| 团队规范、领域规则、质量要求 | `.omtre/spec/` |
| 本次需求、设计、执行计划和上下文 | `.omtre/tasks/` |
| 每个开发者做过什么、上次停在哪 | `.omtre/workspace/` |
| 实现、检查、研究各自的角色边界 | `.omtre/agents/` |
| 任务状态、验证、归档、会话记录 | `.omtre/scripts/` 与任务文件 |

## 一次任务留下什么

```mermaid
flowchart LR
    A[需求与约束<br/>prd.md] --> B[技术设计与执行计划<br/>design.md / implement.md]
    B --> C[代码与测试<br/>任务分支]
    C --> D[检查证据<br/>lint / typecheck / test]
    D --> E[归档与日志<br/>archive / journal]
    E -.可复用经验.-> F[团队规范<br/>.omtre/spec/]
```

这几类内容分别回答不同工程问题：

- **PRD (`prd.md`)**：明确业务目标、变更范围（In scope）、严格排除项（Out of scope）与可量化的验收条件；
- **技术设计 (`design.md`)**：澄清跨层边界、数据流依赖、向后兼容性与回滚策略；
- **执行计划 (`implement.md`)**：规划实施切片、限定影响文件清单，并声明必须通过的验证契约；
- **代码与测试 (`git diff`)**：限定在 PRD 划定边界内的业务实现与对应测试用例；
- **会话日志与规范 (`journal` / `spec`)**：沉淀开发者当次排障过程，并将高价值模式反哺进团队规范合约。

## omtre 是什么，不是什么

| omtre 是 | omtre 不是 |
|---|---|
| 仓库内的工作流与知识结构 | 新的 AI 模型或代码生成服务 |
| 对多种编码代理的平台适配层 | 保证 22 个平台行为完全一致的抽象层 |
| 一套可被 Agent 读取的规范和任务协议 | 不可绕过的操作系统级安全沙箱 |
| 任务、验证、归档的自动化脚本集合 | 自动提交、自动合并、自动上线的交付系统 |
| 让约定和证据进入 Code Review 的工具 | 替代人类工程师做架构决断的自动化终审者 |

::: warning 关键边界：机械阻断 vs 提示词建议
必须清楚区分两类约束：
- **脚本机械阻断（Hard Gate）**：
  - 任务登记了验证契约且未显式跳过时，命令返回非 0 会拒绝归档；`--skip-verify "<reason>"` 会记录原因并绕过本次重放；
  - 缺少 `.omtre/.developer` 时，`add_session.py` 会要求先初始化本地开发者名。该文件只是身份标记，不是登录凭据，也不参与权限校验；
  - 参数缺失或路径非法时，脚本直接退出并报错。
  这些是由本地 Python/Node 脚本在运行时执行判定的刚性闸门。
- **提示词与工作流建议（Soft Guidance）**：
  - “先编写 PRD 再进入实现”；
  - “改动文件严格控制在 3 个以内”；
  - “实现时遵循特定分层架构规范”。
  这些本质上是注入给 Agent 上下文的系统指令（Prompt）。**提示词约束不是安全沙箱**，Agent 仍有概率发生幻觉或越界动作。生产环境的最终防线是人类工程师的审查与 CI 门禁。
:::

## 它和单独的规则文件有什么不同

`AGENTS.md`、`CLAUDE.md` 或 `.cursorrules` 适合保存长期通用的全局约定。omtre 在这些顶层入口之外，补齐了动态任务生命周期与本地证据链：

| 对比项 | 单一规则文件 | omtre |
|---|---|---|
| 规范如何进入会话 | 通常整份无差别加载 | 通过规范索引、任务上下文与平台适配路径按需加载 |
| 本次任务边界 | 容易只留存在聊天窗口中 | 落盘为 `prd.md`、`design.md`、`implement.md` |
| 跨会话记忆 | 依赖模型窗口或个人手工整理 | 开发者个人 workspace 与专属 journal |
| 检查证据 | 仅由当前会话口头报告 | 任务可登记验证命令，并在归档时重放；显式跳过会留下原因 |
| 多代理协作 | 每个平台各自编写维护一套 | 共用 `.omtre/` 核心主轴，平台文件仅作为薄适配层 |

::: tip 作者建议：什么场景适合用，什么场景坚决不要用
如果你的项目只是几百行脚本的日常工具、一次性原型验证（POC），或者属于单人开发且无需跨周期协同的小仓库，直接维护一个清晰的 `AGENTS.md` 往往是 ROI 更高的务实选择；切忌为了追求形式感而强行引入全套任务生命周期。

但如果项目满足以下任一特征，omtre 的工程价值就会非常显著：
- 核心代码有一定规模，关键架构约定与历史妥协长期停留在资深工程师脑中；
- 团队多人混用不同 AI 宿主，需要一套统一、同源的规范和事实入口；
- 需求变更跨越多个文件或模块分层，一次对话无法完成，需要保留计划与设计依据；
- 团队重视代码审查质量，要求 AI 交付的代码必须携带明确的范围声明与测试证据。
:::

## 坚决不要直接使用的场景（红灯）

以下情况说明前置基础设施尚未成熟，此时引入 omtre 只会增加流程阻碍：

- **仓库缺乏自动化检查基础**：项目中连一条能稳定跑通的 lint、类型检查或单测命令都没有（omtre 的验证闸门无法凭空发挥阻断作用）；
- **放弃人工审查的放任上线**：团队缺少 PR Code Review 机制，期望让 Agent 无人值守直接向主干合代码并上线；
- **首次试用就碰高危敏感路径**：首次接入 omtre 就试图拿核心鉴权、交易支付、线上数据库变更或生产部署配置做试验；
- **误将工作流当防注入沙箱**：指望靠框架拦截任意恶意的 Bash 执行（此类防护必须由系统级容器或操作系统沙箱承载）。

## 核心概念

| 概念 | 工程含义 |
|---|---|
| **规范（spec）** | 存放在 `.omtre/spec/`，定义分层架构、约定与可验证的质量要求 |
| **任务（task）** | 存放在 `.omtre/tasks/`，单次业务变更实体，包含需求、设计与状态文件 |
| **验证契约（verification contract）** | 绑定在任务上的真实 shell 验证命令，归档时可由脚本重放并检查退出码 |
| **任务归档（archive）** | 将完成任务移入 `.omtre/tasks/archive/`。默认还会创建仅包含任务簿记的本地提交，不含业务代码；`session_auto_commit: false` 或 `--no-commit` 可关闭 |
| **开发者工作区（workspace）** | 存放在 `.omtre/workspace/<name>/`，记录个人会话日志与跨会话线索 |
| **平台适配层（platform adapter）** | 生成的 `.claude/`、`.cursor/`、`AGENTS.md` 等宿主配置文件，让不同 Agent 读取同一份事实 |
| **写入者（writer）** | 本地开发者标识，用于任务归属、日志目录和 `--mine` 过滤；不是鉴权身份 |
