# 真实场景

<MaturityBadge level="mixed" />

这一页不是命令列表，而是七条可落地的起点。每条都给出适用情况、起始提示、应留下的产物和完成标准。选择最接近你当前问题的一条。

## 场景地图

| 场景 | 适用情况 | 主要价值 |
|---|---|---|
| 1. 新项目 | 从零搭建产品、服务或内部工具 | 在模式扩散前写清早期决定 |
| 2. 接入已有项目 | 约定藏在旧 PR、老成员和零散文档里 | 从真实代码提取规范，不造空中规则 |
| 3. 交付跨层功能 | 改动同时涉及 UI、API、数据或权限 | 让范围、契约和验证一致 |
| 4. 重构旧模块 | 能运行但难改、难测 | 先固定行为，再改变结构 |
| 5. 修重复缺陷 | 同一类问题反复出现 | 把修复变成测试和规范 |
| 6. 收敛 Review 反馈 | Reviewer 一直重复同类意见 | 把反馈变成可执行检查 |
| 7. 团队试点 | 多人、多工具、多个仓库准备接入 | 小范围验证后再推广 |

> 先完成一个有用任务，再增加规范。一个空而完整的规范库，价值低于一组有真实代码证据的规则。

## 1. 启动新项目

### 适用情况

你正在建立一个新的产品、服务、SDK 或内部工具。AI 可以加速，但你不希望每次会话重新发明目录结构、API 风格、错误格式和测试方式。

### 起始提示

```text
这是项目的第一周。请先不要写业务代码。

根据当前目标和技术栈，帮我：
1. 识别已经确定的架构与产品决策；
2. 只写当前任务真正需要的规范：目录结构、API 边界、错误处理、测试策略；
3. 创建第一个可端到端验证的纵向功能任务；
4. 每条规范必须说明为什么，并引用已有文件或明确标注为待决策。
```

### 工作流

1. 创建最小 PRD，明确第一个纵向切片。
2. 只写已经有证据的规范，不要预设计整个项目的架构。
3. 选一个从入口到测试都能验证的小功能。
4. 完成实现、检查、提交和归档。
5. 从这次任务中提炼第一条真实规范。

### 完成标准

- 新成员能读懂 PRD 的范围和验收条件；
- 仓库有真实可运行的检查命令；
- 规范描述已有决定，而不是愿望；
- journal 记录技术栈和早期取舍。

## 2. 接入已有项目

### 适用情况

代码已经存在，约定散落在旧 PR、Review 习惯、资深成员记忆和零散文档中。Agent 能改代码，但经常漏掉本地细节。

### 起始提示

```text
这是一个已有仓库。请先不要重构。

扫描真实代码，提出一个最小 omtre 接入方案。重点识别现有的：
- API 路由与错误格式；
- 鉴权和权限检查；
- 日志与配置；
- 测试组织方式；
- 前端表单与异步状态。

只写能从当前代码找到例子的规范。每条给出来源文件路径。
如果证据不足，列为待确认，不要编造规则。
```

### 工作流

1. 初始化 omtre，生成基础工作流。
2. 选择 3–5 个有代表性的真实调用链进行阅读。
3. 写少量规范，每条引用真实文件。
4. 选一个低风险试点功能，验证规范是否减少重复解释。
5. 删除无法追溯或没有约束力的空泛规则。

### 安全边界

- 不要把目标架构写成现状；
- 不要第一次就为所有包生成完整规范；
- 首个试点不要涉及数据库迁移、鉴权或生产配置；
- 迁移现有旧上游项目是独立操作，详见[旧项目迁移](../advanced/migration.md)。

### 完成标准

- 规范有真实代码证据；
- 试点任务减少了本地约定提醒；
- Reviewer 可以指向规范文件，而不是反复口头解释。

## 3. 交付跨层功能

### 适用情况

功能同时涉及产品行为、UI、API、数据库、权限和测试。例如团队邀请、订单筛选或账单状态。

### 起始提示

```text
为“<功能名>”创建一个 omtre 任务。

请覆盖：
- 用户可见行为；
- In scope / Out of scope；
- API 或数据契约变化；
- 权限和失败路径；
- 前端状态；
- 测试与回滚计划。

先写 PRD。涉及多个层或引入数据变化时，再写 design.md 和 implement.md。
```

### 工作流

1. **任务边界**：一个任务对应一个可独立验收的交付物。
2. **计划产物**：PRD 写需求，design 写边界和数据流，implement 写顺序与验证。
3. **上下文清单**：把相关规范和调研加入 `implement.jsonl` / `check.jsonl`。
4. **实现**：先形成最小纵向路径，再补边界分支。
5. **检查**：分别从规范符合性和真实命令验证两个方向检查。
6. **人工 Review**：确认产品行为、错误路径和范围没有漂移。

### 拆任务原则

同一任务内可以拆实现步骤，但以下情况应拆成独立任务：

- 有自己的发布或落库边界；
- 可以独立验收和回滚；
- 与主功能之间不存在必须同时上线的关系。

### 完成标准

- PRD 的验收条件逐条有证据；
- API、UI 和持久化边界一致；
- 失败路径有测试；
- 范围外工作没有混入 diff。

## 4. 重构旧模块

### 适用情况

一个模块能工作，但职责过多、难以测试、修改风险高。典型例子是一个服务同时计算、访问数据库、调用第三方并生成邮件。

### 起始提示

```text
为 <模块路径> 创建一个行为保持的重构任务。

先不要改代码。请先映射：
- 当前职责；
- 调用方和副作用；
- 现有测试覆盖；
- 无法从代码确认的行为。

在确认特征测试或现有覆盖前，不要开始拆分。公开接口默认保持不变。
```

### 工作流

1. 在 PRD 中列出“行为不能改变”的不变量。
2. 先运行现有测试，记录基线。
3. 为关键路径补特征测试。
4. 每轮只抽取一个职责，保持公开接口稳定。
5. 每轮之后运行同一组验证。
6. 把新的模块边界写回规范（如果它将成为长期规则）。

### 完成标准

- 重构前后关键行为一致；
- 测试可以在重构失败时发现问题；
- 每轮 diff 可以独立审查；
- 规范记录新的模块边界和依赖方向。

## 5. 修重复出现的缺陷

### 适用情况

表面上修过，但同类问题再次发生。仅修症状不会阻止下一次。

### 起始提示

```text
修复 <缺陷>。先把现象变成可重复失败。

请：
1. 写出最小复现；
2. 定位根因，而不是只改报错位置；
3. 先补会失败的回归测试，再修复；
4. 检查同一模式是否存在于其它调用链；
5. 提出一个防止复发的机制：测试、类型、lint、检查清单或规范。
```

### 工作流

1. 在 PRD 中记录现象、重现步骤和预期行为。
2. 先做失败测试，确认它真的能捕获问题。
3. 修复最小根因。
4. 检查同类模式。
5. 把可复用的预防措施写进规范或测试工具。
6. 在 journal 中记录根因，而不只是提交号。

### 完成标准

- 回归测试在修复前失败、修复后通过；
- 根因写在任务或 journal 中；
- 预防机制存在于代码或规范，不只在聊天里；
- 同类调用链已有明确结论。

## 6. 收敛重复的 Review 反馈

### 适用情况

Reviewer 反复指出同样的问题：缺少 loading 状态、错误格式不统一、没有回归测试、日期格式化重复、SQL 不安全等。

### 起始提示

```text
分析最近 <N> 个 PR 的重复 Review 意见，帮我转成最少量的 omtre 规范。

只保留：
- 能从真实意见追溯；
- 可以明确判断是否违反；
- 能用好/坏示例说明。

每条给出目标规范文件、触发条件和验证方式。
无法执行的建议不要写入规范。
```

### 工作流

1. 收集真实 Review 意见，按工程规则分组。
2. 一组规则只放一个规范文件。
3. 用现有代码写好坏例，不要编造。
4. 把规范加入下一批任务的检查上下文。
5. 观察规则是否真的发现问题、是否产生噪声。
6. 删除无效规则，保留有效规则。

### 完成标准

- 每条规范能追溯到一个真实问题；
- Reviewer 能引用规范而不是重复解释；
- 新任务中同类反馈减少；
- 规范没有膨胀成无法执行的宣言。

## 7. 团队试点

### 适用情况

多名开发者、多个 AI 工具或多个仓库准备接入。

### 起始提示

```text
为一个试点仓库制定两周 omtre 接入方案。

包含：
- 试点参与者和实际使用的平台；
- 首个低风险业务任务；
- 首批 3–5 条规范；
- 验证命令与人工 Review 流程；
- 成功指标、退出标准和风险。
不要启用无人值守推送。
```

### 推荐试点范围

- 1–2 个非关键仓库；
- 3–5 名成员；
- 只接团队实际使用的 1–2 个平台；
- 保持人工 commit、push、PR；
- 显式设置 `verify_required: true`；
- 不默认安装全量市场技能。

### 指标

- 首个业务任务的完成时间和卡点；
- 跨会话重复解释是否减少；
- PRD 的范围外工作是否减少；
- 重复 Review 意见是否减少；
- 任务文档维护成本是否可接受；
- 是否出现未批准推送、文件丢失或验证绕过。

### 退出标准

任一情况持续出现时，先停止扩大试点：

- 团队为了填文档而填文档；
- 规范与真实代码脱节；
- 开发者绕过验证或归档；
- 平台 hooks 不稳定；
- 维护任务产物的成本明显高于收益。

## 选择最小的下一步

如果你不确定从哪里开始：

- 新仓库：先生成一个最小规范和第一个纵向任务；
- 已有仓库：先读真实代码，再写第一条有证据的规范；
- 重构：先固定行为不变量和测试基线；
- 团队：先在一个仓库完成一个真实任务，再谈统一推广。
