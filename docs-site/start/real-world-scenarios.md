# 真实场景

<MaturityBadge level="mixed" />

将 omtre 引入工程实践不是一次性的架构重构，而是针对具体研发痛点选择对应的交付技术模式。以下七个落地场景给出了清晰的适用边界、准入判断、工作流与完成标准。

## 场景地图与准入前置

| 场景 | 适用情况 | 核心价值 | 准入前置判断（何时直接接入 / 何时先补门禁） |
|---|---|---|---|
| 1. 新项目初始化 | 从零搭建服务、SDK 或内部工具 | 在代码扩散前确立架构基线 | 直接接入，在首次提交前建立验证命令基线 |
| 2. 接入已有项目 | 规范散落在历史 PR 与成员记忆中 | 提取代码真实证据，避免空中楼阁 | **已有单测可直接接入；测试缺失必须先补门禁再试点** |
| 3. 交付跨层功能 | 改动同时涉及 UI、API、数据模型 | 保持需求、契约与验证强一致 | 契约接口稳定可直接做；未定契约必须先冻结接口 |
| 4. 重构旧模块 | 逻辑可用但高耦合、缺乏可维护性 | 固定行为不变量，安全解耦架构 | **严禁零测试重构；必须先补特征测试网再动工** |
| 5. 根治重复缺陷 | 同类问题反复出现、修表面留隐患 | 将缺陷收敛为硬性回归测试 | 必须具备编写本地失败用例的能力，否则先搭建测试环境 |
| 6. 收敛 Review 意见 | 审阅人员反复指出相同的反模式 | 将人工意见转化为机器门禁与规范 | 优先转化为 linter/类型规则；无法机械化的再入规范 |
| 7. 团队试点推广 | 多成员、多平台准备统一研发流水线 | 在局部受控验证人机协同 ROI | 选 1 个非核心仓库先行；严禁在全缺乏门禁的仓库推广 |

## 1. 启动新项目

### 适用情况与工程判断

从零构建新产品、服务或 SDK 时，模型能够极大加速样板代码编写，但极易在缺乏规范的情况下在每次会话中“发明”不同的目录结构、错误处理规范与 API 签名。
**准入判断**：新项目适合**直接接入**。在写下任何实际业务逻辑之前，必须先把本地验证命令（如 lint、typecheck、基础单元测试）和目录拓扑固定下来。

### 起始提示

```text
这是项目初始阶段。请先不要编写实际业务代码。

根据当前目标和技术栈，帮我完成技术准备：
1. 识别已确定的基础架构与技术选型决策；
2. 仅编写当前必需的基础规范：目录布局、API 契约边界、错误处理格式与测试策略；
3. 创建第一个具备端到端验证能力的纵向切片任务；
4. 所有规范必须说明工程理由，并明确标注待定项。
```

### 标准工作流

1. 执行 `task.py create` 初始化首个纵向切片任务，通过 `prd.md` 划定范围；
2. 仅固化已有技术决策的规范，避免过早过度设计全局规范；
3. 完成最小可用链路的编码与本地验证；
4. 提交代码并执行归档，将沉淀下的架构规则写回规范库。

### 完成标准

- 仓库内存在通过退出码校验的确定性检查命令（如 `pnpm test` 或 `pytest`）；
- `prd.md` 明确声明了第一批 In Scope 与 Out of Scope；
- 规范中记录的是已确立的技术事实，而非假设愿望；
- workspace journal 记录了技术选型的权衡证据。

## 2. 接入已有存量项目

### 适用情况与工程判断

存量项目已有大量历史代码，约定往往零散存在于旧 PR、Review 习惯或老成员记忆中。
**作者核心判断**：
- **何时适合直接接入**：项目拥有可运行的测试套件（单测/集成测试）、构建脚本可在几分钟内输出确定性退出码（0/1）。此时可直接初始化 omtre，选取 3–5 个代表性调用链提取规范并推进业务任务。
- **何时必须先补齐门禁**：项目缺乏自动化测试、构建脚本常年报错或仅能依靠人工黑盒点点看。**此时严禁直接让 Agent 修改业务逻辑**，首个 omtre 任务必须定义为“为目标模块建立基础测试脚手架与自动化验证命令”，门禁就绪前，任何 Agent 业务改动都会引入难以排查的代码退化。

### 起始提示

```text
这是一个已有存量仓库。请先不要修改任何代码。

扫描当前代码实现，输出最小接入方案。重点提取以下维度的现有实现模式：
- 现有 API 路由与错误返回结构；
- 鉴权与上下文传递方式；
- 配置读取与日志打印规范；
- 单元测试与 mock 组织模式。

每条规范必须引用 1–2 个真实代码文件路径作为证据。
若证据不足，标记为“待确认”，严禁自行编造理想规则。
```

### 标准工作流

1. 运行 `omtre init` 初始化配置；
2. 审查 3–5 个核心模块，提取具有代码证据的基线规则；
3. 选取一个极低风险的边缘功能进行小范围试点；
4. 验证规范是否减少了会话中的反复提示；
5. 剔除无法追溯至源码的空泛规则。

### 刚性红线

- 绝不将“理想架构目标”写成“现状规范”；
- 首次试点任务绝对不要触碰鉴权流、核心数据库迁移与生产配置文件。

## 3. 交付跨层功能

### 适用情况与工程判断

功能变动横跨数据持久化、后端 API、鉴权逻辑与前端界面交互。
**作者核心判断**：跨层任务最大的失控点在于“在接口与数据模型未冻结前，模型凭猜测同步写完了前后端，最终联调全盘重构”。
必须执行**设计阶段强依赖**：涉及数据库或网络契约变动时，必须首先在 `prd.md` 和 `design.md` 中冻结契约接口，并通过局部 mock 校验后，才允许开启具体编码。若前后端跨越不同代码库且未建立端到端契约测试，必须拆分为两个独立任务逐一推进。

### 起始提示

```text
为“<功能名称>”创建 omtre 任务。

请按序推进设计：
1. 明确用户行为与边界（严格划分 In scope 与 Out of scope）；
2. 冻结底层数据模型与对外 API 契约变化；
3. 声明异常分支、鉴权要求与前端状态机；
4. 输出本地可执行的自动化验证策略与回滚预案。

先完成 prd.md 与 design.md，经确认后再编写 implement.md。
```

### 任务拆分准则

若满足以下任一条件，必须拆分为独立任务，严禁打包在同一会话中：
- 具备独立的数据库迁移发布依赖；
- 可单独合并上线并在生产环境通过 Feature Flag 隔离；
- 由不同角色或团队进行代码 Review。

### 完成标准

- API 契约、数据层变更与前端视图状态强一致；
- 异常路径与鉴权失败路径具备自动化用例覆盖；
- `git diff` 干净，不存在 PRD 约定外的多余改动。

## 4. 重构旧模块

### 适用情况与工程判断

模块核心逻辑能够工作，但职责过载、依赖杂乱、可维护性差。
**作者核心判断**：**严禁在缺乏测试保护网的遗留代码上直接发起重构**。
- **准入前置**：必须在重构前确立“行为不变量”。若原有测试覆盖不足，**必须先补齐特征测试（Characterization Tests）**，用黑盒用例锁定输入输出与副作用。只有在现有测试命令能可靠变绿、在逻辑篡改时可靠报红的前提下，才允许执行 `task.py start` 开始代码结构重构。

### 起始提示

```text
为 <模块路径> 创建行为保持的重构任务。严禁改动任何对外可见的业务行为。

重构前置分析：
1. 梳理当前模块承担的完整职责与外部调用方；
2. 统计现有的单元测试覆盖；若关键路径缺乏测试，先列出需补齐的特征测试清单；
3. 锁定保持不变的公开接口与数据结构。

在特征测试编写完毕且退出码为 0 之前，不要开始拆解源码。
```

### 标准工作流

1. 在 `prd.md` 中精确枚举“绝对不允许改变”的行为不变量；
2. 补充特征测试，建立回归验证基线；
3. 单次迭代仅抽取一个独立职责，保持外部签名向后兼容；
4. 每次改动后机械重放同一组验证契约；
5. 将提炼后的模块边界沉淀为架构规范。

### 完成标准

- 重构前后核心特征测试全部通过，无退化缺陷；
- 每一个 Git Commit 保持独立可审查，不把重构与新功能混杂。

## 5. 根治重复缺陷

### 适用情况与工程判断

同一类型缺陷反复出现，以往仅在表面打补丁，未能阻断衍生问题。
**作者核心判断**：**凡未包含“先失败后通过”的可重现回归测试的 Bug 修复，一律视为未完成**。自然语言描述的“已修复”不可信，只有通过自动化测试真实复现红灯、修复后转为绿灯，才具备归档准入资格。

### 起始提示

```text
排查并修复缺陷：<缺陷描述与错误日志>。

严格按以下步骤处理：
1. 定位缺陷产生的底层根本原因，而不是在报错点做空值判断；
2. 编写一个最小复现的自动化失败用例，证明其能稳定捕获该 Bug；
3. 实施针对根本原因的最小源码修改，使该测试变绿；
4. 扫描项目中是否存在同类反模式的调用点；
5. 提供防止再次发生的机制（如补充 lint 规则、类型守卫或架构规范）。
```

### 完成标准

- 新增回归测试在修复前退出码非 0、修复后退出码为 0；
- 根因分析记录于 PRD 与 journal，而非丢失在聊天记录中；
- 关联的所有潜在同类调用点均已排查并给出结论。

## 6. 收敛重复的 Review 反馈

### 适用情况与工程判断

代码评审中，资深工程师反复就相同的问题提出修改建议（如错误包装缺失、SQL 未参数化、命名不规范）。
**作者核心判断**：
- **凡是能通过 Linter、TypeScript 编译检查或预提交脚本机械校验的规则，坚决不要写成自然语言 Prompt**；
- 只有当前静态分析工具无法覆盖的语义层设计（如业务分层隔离、模块所有权划分、特定领域命名），才应沉淀进 `.omtre/spec/`。

### 起始提示

```text
分析最近 <N> 次 PR 中的高频 Review 反馈，收敛为最少量的工程约束。

筛选标准：
1. 优先剔除能够通过配置 ESLint/TS 编译器机械拦截的规则；
2. 针对无法静态检查但重要的设计约定，按模块收敛到对应 spec 规范中；
3. 每条规则必须包含来源于真实代码的“正确示范”与“反模式示范”。
```

### 完成标准

- 每条规范直接对应过去发生的真实 Review 痛点；
- 新代码生成阶段，同类反模式的出现频次显著下降；
- 规范文件精简克制，未膨胀为无法落地的空洞倡议。

## 7. 团队试点推广

### 适用情况与工程判断

团队计划在多位成员、多个服务中标准化引入 omtre 体系。
**作者核心判断**：**严禁在缺乏基础 CI 门禁的团队中直接开启全员无干预自动化（`omtre run`）**。在团队试点阶段，必须锁定 `verify_required: true`，严格保留人工审查 `git diff` 与人工提交的防线。

### 试点配置与范围控制

- **试点规模**：选择 1–2 个具备自动化测试的非核心业务仓库，参与人员 3–5 人；
- **平台范围**：收敛到团队主力使用的 1 个 Agent 工具或宿主；
- **硬性门禁**：在 `.omtre/config.yaml` 中配置 `verify_required: true`，杜绝未验证任务归档；
- **交付权限**：关闭全自动分支推送，严禁赋予模型对主分支的直接 Push 权限。

### 准入与退出准则

**准入标准**：试点仓库必须已有通过的单测/Lint 脚本，项目骨架清晰。
**熔断退出机制**：若出现以下情况，应立即暂停扩大试点并反思复盘：
1. 团队为了满足任务格式而大量填写应付型空文档；
2. 规范与业务代码严重脱节，且无测试进行重放；
3. 开发者频繁使用跳过验证或手工修改任务状态机；
4. 会话辅助耗时明显高于人工独立编码收益。

## 核心实践决策清单

- **新仓库**：直接初始化，以建立最小验证命令与单测脚手架为第一任务；
- **存量仓库**：**无测试不接 Agent**。测试缺失时，首个任务必须是补足门禁，严禁直接让 Agent 重构或改动核心业务代码；
- **复杂重构**：先编写特征测试锁定行为不变量，再开始模块解耦；
- **团队协作**：人管 Git 与 PR，机器负责契约重放与本地状态记录。
